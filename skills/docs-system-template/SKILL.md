# AI Agent 项目文档体系模板（按阅读场景分层）

目标：**让 Agent（和新人）在开工时只读必读的几 KB，而不是通读整个 docs/；让每份文档能用一句话回答「什么时候读我」。**

两条根原则（其余一切规则都是它们的推论）：
1. **按阅读场景组织，不按内容类别堆放** —— Agent 的成本在「读什么」，不在「写了什么」。同一份文档里「每次开工都要读的」和「一年查一次的」绝不能放一起。
2. **单一权威源** —— 同一事实只在唯一权威源写一次，其他位置写「见 `X.md` §Y」（**引用必须带节号**）。副本是 token 放大器：一份事实有 2–4 个互相矛盾的副本时，Agent 不敢只读一份，必须全读再仲裁。

> 与姊妹 skill 的分工：**新项目从零搭建 → 用本文（模板 + 落地步骤）**；**存量文档已经膨胀、需要重构 → 用 `docs-split-by-reading-scenario`**（量化诊断、零损失搬运、拆分手法）。两者的体积预算、头部元数据、归档编号规则同源一致。

## 0. 目录结构总览

```
docs/
├── <前缀>_0 文档地图.md        ← L0 地图层：唯一入口索引（哪个问题读哪份）
├── AGENTS.md                   ← L1 必读层：纪律 / 红线 / 协作 / 禁令
├── Agent交办事项.md            ← L1 必读层：现在在哪、下一步做什么、等谁拍板
├── AGENTS_记录规范.md          ← 开工前置：写开发记录前才读
├── AGENTS_平台规范.md          ← 开工前置：构建 / 模拟器 / 验收平台口径
├── 文档维护约定.md             ← 仅调整文档结构时读（体系规则的权威源）
├── <前缀>_1 功能与逻辑.md      ← L2 按需层：业务规则基线
├── <前缀>_2 产品设计与信息架构.md
├── <前缀>_2b/2c/2d/2e/2f …    ← 字母后缀子文档（不进必读路径）
├── <前缀>_3 交付状态.md        ← L2 状态类：进度 / 测试基线 / 验证边界
├── <前缀>_3b/3c/3d/3e …       ← 待决策 / 技术债 / 测试门槛 / 交付明细
├── <前缀>_4 界面改版方案.md    ← 按主题继续编号
├── engineering/                ← 规则的「为什么」、原理与排障（按需层）
├── development-logs/           ← 流水：逐次开发记录（不设体积上限、不通读）
│   ├── TEMPLATE.md             ← 记录模板（新建必须从它复制）
│   ├── README.md               ← 总索引（按时间倒序）
│   └── YYYY-MM/YYYY-MM-DD-HHmm_<agent-id>_<topic>.md
├── archive/                    ← L3 历史归档：原文一字不改、非追溯不读
│   ├── README.md               ← 索引（不编号）
│   └── A01 变更史.md …         ← 「A + 两位序号 + 空格 + 名称」
└── tools/doc-size.sh           ← 收尾体积自检脚本（只读，越线退出码 1）

skill/                          ← 自产技能包（不在 docs/ 预算内；见下 §9 注意）
```

> `<前缀>` 是项目代号（如 `Protick_`），用来把文档绑定到项目、避免复制到别处时混淆。**同一项目内前缀必须一致**；脚本、地图、预算表三处引用同一个前缀口径。

## 1. 文档清单：每份文档的职责与「什么时候读我」

新项目**最小可行集只有 5 件**：`<前缀>_0 文档地图` + `AGENTS.md` + `Agent交办事项` + `AGENTS_记录规范` + `development-logs/`（TEMPLATE + README）。其余按项目长大逐份增设——**每增设一份，都要先回答「哪个场景读它」，答不出就不建**。

| 层 | 文件 | 职责（一句话） | 什么时候读 | 上限 |
|---|---|---|---|---:|
| L0 | `<前缀>_0 文档地图.md` | 「想知道什么 → 读哪份」的路由表 + 阅读场景表 | **每次开工第一个读**，然后只读需要的 | 8 KB |
| L1 | `AGENTS.md` | 纪律、红线、禁令、协作方式、硬约束 | 每次开工必读 | 28 KB |
| L1 | `Agent交办事项.md` | 当前状态、下一步、待用户拍板项 | 每次开工必读 | 20 KB |
| 前置 | `AGENTS_记录规范.md` | 开发记录放哪、怎么命名、字段怎么填 | 新建 / 更新记录前 | 8 KB |
| 前置 | `AGENTS_平台规范.md` | 模拟器 / 平台 / 验收口径 | 构建、跑测试前 | 8 KB |
| 维护 | `文档维护约定.md` | 体系规则本身：预算 / 拆分 / 权威源 / 归档编号 | 调整文档结构时 | 8 KB |
| L2 | `<前缀>_1 功能与逻辑.md` | 业务规则基线（需求口径） | 确认业务口径 | 24 KB |
| L2 | `<前缀>_2 产品设计与信息架构.md` | 产品形态、信息架构、为什么这么定 | 做产品决策 | 24 KB |
| L2 | `<前缀>_2b/2f …` | 某主题的展开（功能设计 / 支撑页） | 改对应功能 | 24 KB |
| L2 | `<前缀>_2c` | 数据模型与视觉规范 | 改 Schema / UI 令牌 | 24 KB |
| L2 | `<前缀>_2d` | 技术方案与质量门槛 | 选型 / 定达标线 | 24 KB |
| L2 | `<前缀>_2e` | 分阶段路线与退出标准 | 排阶段计划 | 24 KB |
| L2 状态 | `<前缀>_3 交付状态.md` | 现在做到哪、测试基线、验证边界 | 查进度 / 验收 | 36 KB |
| L2 状态 | `<前缀>_3b 待决策与验收.md` | 等谁拍板、怎么人工验收 | 决策 / 人工验收 | 36 KB |
| L2 状态 | `<前缀>_3c 技术债与风险.md` | 还欠什么 | 排期 / 还债 | 36 KB |
| L2 状态 | `<前缀>_3d 测试门槛状态.md` | 测试门槛逐条状态 | 定发布条件 | 36 KB |
| L2 状态 | `<前缀>_3e 交付明细与对照矩阵.md` | 每个交付项的证据 | 核对某交付项 | 36 KB |
| L2 | `<前缀>_4 界面改版方案.md` | 界面还要改什么 | 做界面 | 24 KB |
| L2 | `engineering/*.md` | 规则的成因、判据、排障手册 | 排障 / 质疑规则时 | 24 KB/份 |
| 流水 | `development-logs/` | 逐次开发记录 | 找某次任务干了什么 | 不设上限 |
| L3 | `archive/` | 历史原文 | 非追溯不读 | 64 KB/份 |

**AGENTS.md 的建议章节骨架**（本项目实测结构）：`§0 开工前检查清单 → §1 纪律（测试与验收如实性）→ §2 多 Agent 协作与开发记录 → §3/§4 外移占位（保留节号）→ §5+ 领域硬约束 → §6 构建与执行纪律 → §7 自动化断言与取证 → §8 禁止事项清单 → §9 引用索引`。**「如实标注未验证」是整份文档的灵魂**：测试没跑就写「未跑」，验证不到就写「未验证」，禁止把「编译通过」记成「测试通过」。

**状态类（`_3*`）与按需层分开、上限更高（36 KB）**：台账以表格为主、信息密度高；但它仍是「查进度」这一场景的读物，不要混入设计推理。

## 2. 头部元数据块（每份文档必写）

```markdown
# 文档标题

> **职责**：这份文档管什么（一句话）。
> **体积**：6.0 KB ｜ **上限**：8 KB ｜ **更新**：2026-09-26（本轮干了什么，一行）
> **上级索引**：`<前缀>_0 文档地图.md` §1
> **本文不包含**：X → `某文档.md` §Y；Y → `某文档.md` §Z
> ⚠️ **什么时候读本文**：……（不满足就别读）
```

- **「本文不包含」是省钱最直接的一行**——Agent 不打开就知道要不要读、该去哪读。
- 头部「体积」必须与实测一致（**R7**：体积失真与断链同级的维护缺陷）；体积用 `wc -c`（1024 进制）实测，**别心算**。
- 「上级索引」保证每份文档都能从地图两跳内到达；孤文档 = 会腐烂的文档。

## 3. 体积预算与维护规则

预算表（默认值，可按项目微调；**只写在 `文档维护约定.md` §1 一处**，脚本与之绑定）：

| 层 | 上限 | 依据 |
|---|---:|---|
| L0 地图层 | 8 KB | 它自己不能成为负担 |
| L1 必读层（AGENTS / 交办） | 28 / 20 KB | 每人每次都读，最贵的字节 |
| 开工前置 | 8 KB | 动手前按需读，不能膨胀 |
| L2 按需层 | 24 KB | 一次读完 ≈ 5.5 K token |
| L2 状态类（表格密集） | 36 KB | 表格信息密度高 |
| L3 归档层 | 64 KB | 归档也要保证「只读其中一份」 |

- **流水不设上限**（development-logs 随记录数单调增长、拆分救不了），但**必须写死「不要通读」**并给替代路径：找最近记录 `ls -t docs/development-logs/YYYY-*/*.md | head -3`；按主题 `grep` 定位后只读命中行。索引 README 会膨胀成几万 KB，**在三处（地图 / 维护约定 / 文件自身头部）都写「不要通读」**。
- **余量阈值**：任何文档余量 < 上限的 5%（或 < 1.5 KB）时，**下一次新增之前先拆**，不要等破线。

七条维护规则（完整推演与重构手法见 `docs-split-by-reading-scenario`）：
- **R1 先归属，后拆分**：多数「太长」是内容错位——先问「这段属于这份文档的职责吗」，不属于就搬走。
- **R2 按阅读场景切**：每份文档必须能一句话回答「什么时候读我」，否则不该存在。
- **R3 命名**：同主题子文档用字母后缀（`_2b`、`_3c`）；**字母后缀一律不进必读路径**；主文档放该主题最高频部分。
- **R4 头部元数据块**（见 §2）。
- **R5 引用代替复制**：只写一处，引用必须带节号。
- **R6 越线即负责**：收尾发现越线当场拆或归档，不留给下一轮、不抬上限。
- **R7 体积与断链同级**：头部体积失真、超预算未处理，都算维护缺陷。

**外移节号时保留原节号**（如原 `AGENTS.md` §3 外移为 `AGENTS_记录规范.md` §3.1–§3.4），旧引用只需换文件名；正文留一行「已外移 + 指针」。

## 4. 阅读场景表与开工三件套

文档地图里放两张表，这是整个体系的路由核心：

**§1 清单表**：「你想知道什么 → 读哪份 → 体积 → 上限」（见 §1 的表）。

**§2 阅读清单表**：按任务聚合，控制单次阅读总量：

| 任务 | 读 | 合计 |
|---|---|---:|
| 接手 / 开工 | 地图 + AGENTS + 交办 + 交付状态 §0–§1 | ~50 KB |
| 确认业务口径 | `_1 功能与逻辑` | ~14 KB |
| 查进度 / 验收 | `_3` + `_3b` | ~50 KB |
| 排障 | AGENTS + `engineering/` | ~48 KB |
| 改某功能 | AGENTS + `_2b` + `_1` | ~50 KB |
| 全量通读（仅首次 / 大重构） | 全部常驻 | ~300 KB |

> 目标形态：**90% 的任务落在 15–80 KB**，全量通读只是兜底。开工三件套 = `AGENTS.md`（纪律）+ `Agent交办事项.md`（现状与下一步）+ `_3 交付状态` §0–§1（进度与验证边界）。

**Agent交办事项.md 的内容骨架**：§0 当前一句话状态 → §1 等用户拍板的事项（每条：问题 / 选项 / 建议）→ §2 下一步任务分解（含前置条件）→ §3 已完成事项指针（详情在开发日志）→ §6 交接注意事项。它是「接力棒」，**只放状态与指针，不放过程**（过程在 development-logs）。

## 5. 开发记录子系统（development-logs/）

**5.1 存放与命名**：`docs/development-logs/YYYY-MM/YYYY-MM-DD-HHmm_<agent-id>_<topic>.md`。`agent-id`、`topic` 只用小写英文字母、数字、连字符；同分钟同名追加 `-02`。**新建必须从 TEMPLATE.md 复制，不得删减必填字段或章节**。新建或完成后**必须同步 README.md 总索引**（按开始时间倒序插表头）。

**5.2 标识与状态**：`record_id = DEV-YYYYMMDD-HHMM-<agent-id>-<topic>`，与文件名对应、项目内唯一。`status` 五值闭环：`planned / in_progress / blocked / completed / cancelled`（不够用可加值如 `user-halted`，但必须进索引的状态图例表）。时间一律 ISO 8601 带时区（`YYYY-MM-DDTHH:mm:ss+08:00`，**不得省略时区**）。

**5.3 frontmatter 模板**（TEMPLATE.md 的头部）：

```yaml
---
record_id: DEV-YYYYMMDD-HHMM-agent-id-topic
title: "任务标题"
status: in_progress
started_at: "YYYY-MM-DDTHH:mm:ss+08:00"
completed_at: null
timezone: "Asia/Shanghai"
agents:
  - id: "agent-id"
    role: "架构设计/开发/测试/验收等"
    primary: true
    contribution: "负责的具体工作"
related_issues: []
related_commits: []
tags: [模块名, feature|bugfix|test|docs, architecture]
---
```

**5.4 正文章节（九段，逐段写）**：目标与背景 / 范围（包含·不包含）/ 方案与关键决策（表：时间·Agent·决策·原因·影响）/ 过程时间线 / 变更清单 / 测试与验收（表：检查项·命令·结果·时间·执行 Agent）/ 问题与踩坑 / 风险技术债与未完成事项 / Agent 协作与交接 / 最终结果。

**5.5 更新流程**：① 开工即建记录、置 `in_progress`、加入索引；② 过程中**持续追加**时间线 / 决策 / 踩坑，**不得交付时一次性补写**；③ 接手、转交、阻塞立即记录；④ 全部检查通过才可置 `completed`；⑤ 取消 / 受阻置 `cancelled` / `blocked`，写明原因与恢复条件。

**5.6 查找**：`rg 'record_id: DEV-'`（按 ID）｜ `rg 'id: <agent-id>'`（按 Agent）｜ `rg 'status: (blocked|in_progress)'`（按状态）｜ `rg '<关键词>'`（按主题）。

**5.7 历史不回改**：记录是**当时状态的原文快照**，完成后不回改、不删减章节。事后状态变化写在**新记录**或索引行内加注（「该记录中 X 已于某日 Y，见 …」），不在原文上修改。

## 6. 归档区（archive/）

1. **原文一字不改**：历史从正文搬来时整段搬运，只加 4 行归档页眉（本文件是历史归档 / 收录范围 / 什么时候读 / 当前状态请读 X）；**历史只换位置、不改字**。「压缩」= 新增摘要 + 原文归档，绝不删减式改写。
2. **不再更新**：历史在这里冻结；新历史由 development-logs 承接。
3. **编号 `A` + 两位序号 + 空格 + 名称**（`A01 变更史.md`）；README 不编号。**新增一律追加到末尾，不复用、不插入、不重排**——否则已发出的外部引用会指向错误内容。这条必须写进 archive/README.md。
4. **引用一律带编号**：写法 `docs/archive/A03 交付明细-阶段0至1.md`。
5. 归档内容若已被提炼进现行规则文档，在 README 里写明「沿革出处 → 现行权威源」的映射，防止有人把归档当规则引用。

## 7. 单一权威源表（写进 文档维护约定.md §4）

冲突时以谁为准。**建表动作本身就是梳理**——填「常见错放位置」列时会把大量错位内容找出来：

| 内容 | 唯一权威源 | 常见错放位置 |
|---|---|---|
| 工程纪律 / 红线 / 禁令 | `AGENTS.md` | 原理案例 → 错放 `engineering/` |
| 规则的成因 / 判据 / 排障 | `engineering/踩坑与原理.md` | —— |
| 开发记录格式 | `AGENTS_记录规范.md` | 索引 README 只留图例与索引 |
| 业务规则 | `<前缀>_1 功能与逻辑.md` | —— |
| 进度 / 技术债 / 待决策 | `<前缀>_3 / 3c / 3b` | —— |
| 数据模型长什么样 | `<前缀>_2c` | 「怎么改不崩」→ `AGENTS.md` 硬约束 |
| 历史原文 | `archive/`（只作沿革，不是规则出处） | —— |

## 8. 收尾自检脚本 doc-size.sh（通用版）

放 `docs/tools/doc-size.sh`，**每次任务收尾前跑一次**；越线退出码 1，可接入 CI。要点：预算值与 `文档维护约定.md` §1 绑定（两处不一致本身就是缺陷）；分类函数**先按路径判归档、再按文件名判**（归档文件名可能含「状态」「规范」等词，按名字判会误档）；汇总里必须输出「开工起点」一行——那是每次接手的固定开销。

```bash
#!/usr/bin/env bash
# doc-size.sh — 文档体积自检（只读，不改动任何文件）
# 用法：bash docs/tools/doc-size.sh   退出码：0=全部在限内 1=越线或缺失
set -u
trap '' PIPE
cd "$(dirname "$0")/.." || exit 2   # → docs/
[ -f AGENTS.md ] || { echo "❌ 不在 docs/ 下运行（脚本必须放 <项目>/docs/tools/）"; exit 2; }
fail=0
limit_of() {
  case "$1" in archive/*) echo 64; return ;; esac                 # 必须最先按路径判
  case "$(basename "$1")" in
    *_0*|文档维护约定.md|AGENTS_记录规范.md|AGENTS_平台规范.md) echo 8  ;;
    AGENTS.md)               echo 28 ;;
    Agent交办事项.md)         echo 20 ;;
    *_3*)                    echo 36 ;;    # 状态类
    *)                       echo 24 ;;    # 按需层（含 engineering/）
  esac
}
show() {
  local f="$1" lim kb bytes mark
  [ -f "$f" ] || { printf "❌ 缺失    %s\n" "$f"; fail=1; return; }
  lim=$(limit_of "$f")
  bytes=$(wc -c < "$f" 2>/dev/null | tr -dc '0-9')
  kb=$(awk -v b="${bytes:-0}" 'BEGIN{printf "%.2f", b/1024}')
  mark="✅ 在限"; awk -v a="$kb" -v b="$lim" 'BEGIN{exit !(a>b)}' && { mark="⚠️ 越线"; fail=1; }
  printf "%s  %7s / %-3s KB  %s\n" "$mark" "$kb" "$lim" "$f"
}
echo "── 开工必读 ──"
show "<前缀>_0 文档地图.md"; show "AGENTS.md"; show "Agent交办事项.md"
echo "── 开工前置 ──"; for f in AGENTS_记录规范.md AGENTS_平台规范.md; do show "$f"; done
echo "── 体系规则 ──"; show "文档维护约定.md"
echo "── L2 按需层 ──"
for f in <前缀>_*.md engineering/*.md; do
  case "$(basename "$f")" in *_0*|*_3*) continue ;; esac; show "$f"
done
echo "── L2 状态类 ──"; for f in <前缀>_3*.md; do show "$f"; done
echo "── L3 归档层 ──"; for f in archive/*.md; do [ "$(basename "$f")" = README.md ] || show "$f"; done
# 汇总：开工起点 = 地图 + 必读，是每次接手的最小固定成本
mustread=$(cat "AGENTS.md" "Agent交办事项.md" 2>/dev/null | wc -c | tr -dc '0-9')
mp=$(cat "<前缀>_0 文档地图.md" 2>/dev/null | wc -c | tr -dc '0-9')
awk -v s=$((mustread+mp)) 'BEGIN{printf "  开工起点（地图+必读）%7.1f KB ≈ %.1f K token\n", s/1024, s/4267}'
exit "$fail"
```

> 通用版用 shell glob 按前缀通配；本项目的实战版（含层级标签、常驻总量汇总、防误拷贝守卫）见本仓库 `docs/tools/doc-size.sh`。

## 9. 新项目落地步骤（约 30 分钟）

1. **定前缀与命名**：选项目代号 `X_`，确认命名规则（`X_数字` 主文档、`X_数字+字母` 子文档）。
2. **建最小可行集**：`docs/` 下建 §1 表中 L0 + L1 两份 + `AGENTS_记录规范`（记录规范可先从本文 §5 直接抄成独立文件）。
3. **建流水与工具**：`development-logs/TEMPLATE.md`（§5.3 + §5.4 九段）+ `development-logs/README.md`（状态图例 + 空索引）+ `docs/tools/doc-size.sh`（§8 改前缀）。
4. **写文档地图**：§1 清单表 + §2 阅读场景表 + 开工三件套说明；每份已有文档补头部元数据块。
5. **写 AGENTS.md**：把项目红线写进去——**至少包含「如实标注未验证」**（测试没跑就写未跑）、引用带节号、收尾必跑 doc-size.sh、提交需用户授权（若适用）。
6. **首轮收尾**：跑 `bash docs/tools/doc-size.sh` 至 EXIT=0；全库 grep 检查引用节号有效。
7. **项目长大再增设**：新增任何文档前先答「哪个场景读它」；`_3*` 状态类在第一次出现「交付项证据查不过来」时拆出 `_3e`，以此类推。

**注意事项**：
- 若项目同时维护 `skill/`（自产技能包）：skill 不受 docs 预算约束、不按文档层管理；索引 README 与 docs 的 archive/README 同为索引不编号；**skill 正文不抄进 docs**，docs 里只写指针。
- 多 Agent 协作时：每个 Agent 开工先读三件套，收尾 = 更新交办事项 + 写/更新开发记录 + 跑体积自检；**新造编号（T-xx / D-xx / A-xx）必须当轮登记**，否则下一轮没人知道它指什么。
- 归档区在**第一次发生大改版或台账重写时**才建立，不必首日就建。

## 10. 实测效果（本模板出处）

本模板蒸馏自 Protick 项目（2026-09-26 文档体系重构，A18 归档有全过程）。重构前台账单文件 477 KB、无人能通读；重构后：

- 常驻文档 21 份约 303 KB，但**开工起点（地图 + 必读）≈ 47 KB ≈ 11 K token**；90% 的任务按阅读场景表落在 14–82 KB；全量通读只发生在首次接手。
- 体积越线由 `doc-size.sh` 收尾强制拦截，越线即拆，预算三次放宽均有记录且以「目标 −75% 未受损」为前提。
- 历史全部进 `archive/`（18 份、原文一字不改），正文只留指针；开发记录逐次落 `development-logs/`（含完整 frontmatter 与九段正文），接手零猜测。
