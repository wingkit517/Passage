# 02 · 产品设计方案

> 项目：旅行工作台（Travel Workbench）
> 参照来源：小红书笔记《旅游攻略提前晒🔥ai工作台夯爆了！》—— 作者 @Reese小姐爱做梦
> 原文链接：`https://www.xiaohongshu.com/explore/6ab235360000000033032b8f`
> 版本：v1.1 ｜ 2026-09-27
> **v1.1 变更**：砍掉「电子手帐 / 旅行箱物件墙」，产品收敛为**纯行程工具**。变更理由与影响面见 §十三 待决策 5。

## 一、产品定位

### 一句话定义

**一个把散落各处的旅行攻略，收敛成一条走得通的路线的工作台。**

### 定位陈述

面向**愿意花时间把行程安排明白**的个人或小团体，提供一个把地点、时段、停留时长、周边吃与看整合进同一张地图的工具。它不追求功能大而全，追求**看起来就想打开、用起来不迷路、到了现场不用临时搜**。

### 三条产品原则

1. **顺路优先于好看。** 用户不想做「哪些地方顺路」这种体力活。路线自动排序必须是默认行为，不是高级功能。
2. **一个主场，做透。** v1 只做一件事：把一份行程排明白、看得懂、走得通。不做行后记录。
3. **地点即内容。** 用户要的不是「一个空地图」，而是「已经有人替你踩过点的地图」。预置攻略内容是产品的护城河。

### 明确的非目标（v1 不做）

- ❌ **行后记录**：电子手帐、照片墙、票根 / 纪念品收纳（v1.1 起明确砍掉）
- ❌ 多人算账、AA 分账（交给 TREK / Spliit）
- ❌ 实时机票比价与 OTA 下单（数据合规与成本都很重）
- ❌ 社交 feed、关注关系、公开社区
- ❌ 覆盖全球所有城市（v1 只做 1–3 个精品城市）

## 二、设计原点：从参照笔记里读到了什么

这一节是整个设计的地基。参照笔记的价值不在「用了什么 AI 工具」，而在**它对旅行攻略这个品类的重新定义**。

### 原文关键表述（摘录）

> 「以前做旅游攻略，都是备忘录记一点、收藏夹存一点，越看越乱。」
>
> 「这才是我想看的旅游攻略！」
>
> 「终于不用再苦哈哈地临时研究哪些地方顺路了！」
>
> 「出发前是旅游攻略，回来以后又变成一份旅行纪念品。」
>
> 「一座城市，一场更自由的旅行。」

### 提炼出的四个洞察

| # | 洞察 | 对应设计决策 |
|---|---|---|
| 1 | **痛点不是「没有攻略」，而是「攻略散落各处、越看越乱」** | 核心价值是**归集与结构化**，不是内容生产 |
| 2 | **用户不想做「顺路计算」这种体力活** | 路线自动排序必须是默认行为，不是高级功能 |
| 3 | **「临时搜」是旅行中最糟糕的体验** | 每个地点必须**预先带齐**吃/看/停留时长/避坑提示 |
| 4 | **「攻略的终点是纪念品」——原文确实这么写，但这是个未被验证的假设** | **v1.1 不跟进。** 它描述的是作者对成品的感受，不等于用户的持续需求。行后记录需要用户主动回来录入，属于高摩擦、低确定性的功能，会稀释 v1 的主线。**先证明行前规划成立，再谈行后。** |

> **关于洞察 4 的处理说明**：原文那句「出发前是旅游攻略，回来以后又变成一份旅行纪念品」是本方案最初的产品假设之一（对应「双主场」结构）。v1.1 明确砍掉，原因是**它把产品的重心从「一次性的规划交付」拉向「需要长期运营的记录工具」**，两者的数据模型、留存逻辑、验收标准完全不同。砍掉之后，产品只需要对一件事负责：**这份行程排得对不对、走得通不通。**

### 参照案例（原文给出的 3 天上海路线）· 已归档

> ⚠️ **2026-09-27 更新**：这段路线是 v1.0 的标杆数据集，但产品实际落地时换成了**澳门**（用户真实行程）。
> 保留此节的原因有两条：① 它是这套信息架构的**来源**，删掉就看不懂设计为什么长这样；
> ② 其中「Day 1 末段刻意绕到北外滩 → 陆家嘴看夜景」这条编排逻辑，
> **直接推翻了「总距离最短」这个排序目标函数**（详见 §8.4 与 §十三 待决策 6）。
> 所以它仍然是有价值的证据，只是不再是待复现的验收标准。

这份路线曾是 v1 的标杆数据集：

| 天 | 主题 | 路线 | 地点数 |
|---|---|---|---|
| Day 1 | 黄浦江西岸 | 新天地 → 豫园 → 外滩 → 北外滩 → 陆家嘴 | 5 |
| Day 2 | 梧桐与艺术 | 武康路 → 安福路 → 思南公馆 → 徐汇滨江 | 4 |
| Day 3 | 寺庙与河湾 | 静安寺 → 愚园路 → 苏州河 → 杨浦滨江 | 4 |

**编排逻辑**（值得作为算法规则沉淀）：
- 每天地点尽量**地理集中**，避免东奔西跑；
- 时段有节奏：上午 / 中午 / 下午 / 日落入夜 / 夜间；
- 一天以**一种气质**收束（Day1 石库门→老城厢→夜景；Day3 静安街区→两条水岸）。

### 原文展示的地点详情结构（这是内容模板的雏形）

以「新天地」「愚园路」「静安寺」三张详情卡为例，字段高度一致：

```
[类型标签] · [一句话气质描述]      例：地标 · 石库门夜色
[建议时段]  [建议停留时长]          例：傍晚至夜间 ｜ 建议停留约 1.5 小时
[正文描述]                        2–3 句，讲清楚"为什么值得来"
[配图]                            1 张建筑/场景插画或照片
[先去吃什么]                      店名 + 地址 + 一句提示
[去哪里看风景]                    点位 + 一句提示
[查看资料来源 ↗]                  可追溯的信息来源
```

## 三、目标用户与核心场景

### 用户画像

**主画像：认真对待一次旅行的人**
- 出行频次：每年 2–5 次，其中 1–2 次是「有准备的深度游」
- 特征：会在小红书/收藏夹囤大量攻略，但真正出发时找不到、理不清
- 动机：**把行程安排明白**——不想到了现场才研究哪儿顺路、附近吃什么
- 设备：手机为主，行前规划时用电脑

**次画像：小团体出行的组织者**
- 1 人做攻略，2–6 人跟随
- 核心诉求：把做好的行程**一次性发出去**，同行人不用装 App

### 两个核心场景

| 场景 | 时机 | 用户要什么 | 产品给什么 |
|---|---|---|---|
| **S1 行前规划** | 出发前 1–4 周 | 把囤的攻略变成一份能执行的行程 | 攻略内容归集 → 挑地点 → 自动排路线 → 出 3 日计划 |
| **S2 行中导航** | 旅行当天 | 现在去哪、怎么走、附近吃什么 | 当天路线视图 + 地点详情 + 一键跳转地图导航 |

> **v1.1 移除**：原 S3「行后记录」场景已删除，理由见 §一 非目标。

**关键设计约束**：S2 场景发生在**手机上、户外、可能没信号**。所以移动端与离线不是可选项。

## 四、产品形态：一个主场，两层视图

### v1.1 的结构决策

v1.0 曾用「旅行箱」隐喻统一行前与行后：箱子里的 12 格物件，出发前打开的是地图，回来后打开的是相机。这个隐喻在**砍掉行后记录之后不再成立**——12 格里有一半是行后物件（照片、票根、纪念品、心情、相机、明信片），留着会自相矛盾。

v1.1 改成**两层视图**，围绕同一份行程数据：

```
┌─────────────────────────────────────────────┐
│              旅行工作台                       │
├──────────────────────┬──────────────────────┤
│   视图一：行程总览     │   视图二：地图工作台    │
│   （先看全局）         │   （再看细节）         │
├──────────────────────┼──────────────────────┤
│ · 行程规模统计         │ · 鸟瞰地图漫游         │
│ · 每天主题与路线串联    │ · 多日行程面板         │
│ · 点击某天直接跳进地图  │ · 地点详情卡           │
│                      │ · 路线自动排序         │
└──────────────────────┴──────────────────────┘
        ↑ 同一份数据的两种读法，不是两个产品 ↑
```

**为什么这样分**：用户打开产品时有两个问题——「这份行程大概是什么样」（全局）和「第 2 天具体怎么走」（细节）。前者用一个总览页回答，后者用地图回答。总览页上的每一天都是进入地图的入口，点击即带着当天的筛选状态跳转。

### 与 v1.0 的差异对照

| | v1.0（双主场） | v1.1（两层视图） |
|---|---|---|
| 首页 | 旅行箱物件墙，12 格带角标 | 行程总览：规模统计 + 每天路线卡 |
| 主场数量 | 2（地图 + 手帐） | 1（地图），加一个总览入口 |
| 数据模型 | 需覆盖行前 + 行后两类实体 | 只需 Trip / Day / Place |
| 留存逻辑 | 依赖用户回来录入 | 不依赖留存，一次性交付 |
| 验收标准 | 含「能写一条手帐」 | 只看行程排得对不对 |

## 五、信息架构

```
旅行工作台
├── 行程总览（视图一）
│   ├── 行程规模统计（天数 / 地点数 / 周边餐饮数 / 建议停留合计）
│   ├── 每日路线卡（主题 + 地点串联 + 停留合计）→ 点击进入地图并定位到当天
│   └── 新建 / 切换行程
│
├── 地图工作台（视图二）
│   ├── 地图画布
│   │   ├── 鸟瞰视角（倾斜 + 3D 建筑）
│   │   ├── 地点标记（按天编号：1-1, 1-2, 2-1…）
│   │   └── 路线虚线（每天一色）
│   ├── 行程面板（左）
│   │   ├── 日期 Tab（总览 / 第 1 天 / 第 2 天 …）
│   │   ├── 当日路线摘要（地点 A → B → C）
│   │   ├── 类型筛选（全部 / 江岸 / 街巷 / 地标）
│   │   └── 当日地点列表（序号 + 时段 + 一句话）
│   └── 地点详情卡（右）
│       ├── 类型 · 气质标签
│       ├── 建议时段 / 建议停留时长
│       ├── 正文描述 + 配图
│       ├── 先去吃什么
│       ├── 去哪里看风景
│       └── 查看资料来源 ↗
│
└── 设置
    ├── 行程管理（天数、城市、同行人）
    └── 数据导出
```

> **v1.1 移除**：「旅行箱（物件格子墙）」与「电子手帐」两个分支已删除。

### 与 TREK 的对应关系（复用映射）

| 本产品模块 | 复用 TREK 能力 | 自建部分 |
|---|---|---|
| 地图工作台 · 行程面板 | Trip / Day / Place 数据模型、拖拽排序、OSRM 路线 | **全部前端**（鸟瞰镜头、虚线动画、详情卡） |
| 地图工作台 · 地点详情 | Places + 附件 + 笔记 | 内容模板、资料来源字段、**预置攻略内容** |
| 行程总览 | Trip 聚合统计 | **全部**（统计口径、每日路线卡） |
| 预算 / 清单 / 协作 | Costs / Lists / Collab 全量复用 | 仅做视觉包装 |
| 导出分享 | GPX / ICS / PDF 导出、公开只读链接 | 单文件离线 HTML 导出（借鉴 travel-plan-viz） |
| 离线 | PWA + IndexedDB + 幂等重放 | 无（直接复用） |

**结论**：后端与数据能力几乎全部可复用，**自建集中在「体验层」**——这正好是开源方案缺失、也是产品价值所在的部分。

> **v1.1 起，「电子手帐」一行从复用映射中移除**：TREK 的 Journey addon 虽然能承载文字记录，但既然产品不做行后，就不该留这条复用路径。

## 六、功能模块与优先级

### P0 — v1 必须做（决定产品是否成立）

| 模块 | 功能 | 验收要点 |
|---|---|---|
| M1 地图工作台 | 鸟瞰地图 + 缩放拖拽 + 地点标记 | 倾斜视角下建筑有立体感；60fps 拖动 |
| M2 行程面板 | 多日 Tab + 当日路线 + 地点列表 | 切换天时地图与列表同步 |
| M3 地点详情卡 | 完整字段（时段/时长/吃/看/来源） | 字段齐全，来源可点开 |
| M4 路线串联 | 按天用彩色虚线串联，跟随地图 | 每天颜色不同，线随地图移动 |
| M5 镜头动效 | 点击地点，镜头平滑飞近 | 过渡自然，不晕（可关闭动效） |
| M6 行程总览页 | 规模统计 + 每日路线卡，点击进入地图 | 打开首页 5 秒内明白「这是几天、去哪、怎么走」 |
| M7 路线自动排序 | 最近邻 + 2-opt，支持锁定锚点 | 排序结果不出现明显折返；可一键回到手工顺序 |

> **v1.1 调整**：原 M6「旅行箱首页」与 M7「电子手帐」删除；原列在 P1 的「行程自动排序」提升为 **P0**——因为洞察 2 已明确它是默认行为而非高级功能，放在 P1 与产品原则自相矛盾。

### P1 — v1.1 增强

- 攻略导入：粘贴小红书/收藏夹内容，AI 抽取为结构化地点
- 同行人只读分享链接
- 单文件离线 HTML 导出
- 离线读写（PWA）
- 每天路线的时间窗校验（避免「上午在氹仔、中午回半岛」这类不可执行的编排）

### P2 — v2 探索

- 多城市支持（v1 只做澳门，做透一个城市再扩）
- 预算与清单（直接复用 TREK）
- 天气与公共交通（复用 TREK）
- AI 对话式调整行程（「第 2 天太赶了，帮我松一点」）

## 七、核心交互流程

### 流程 A：从零到一份行程（行前）

```
打开首页（行程总览）
   ↓ 点「新建行程」
选城市（v1：澳门）+ 天数
   ↓
系统给出「推荐路线」候选（基于预置攻略库）
   ↓ 用户勾选想去的 / 划掉不想去的
   ↓
地图工作台生成：每天自动分组 + 按地理集中度排序
   ↓ 用户拖拽微调（地点可在天之间拖）
   ↓
点任意地点 → 详情卡展开 → 看吃什么、看什么、停留多久
   ↓
行程定稿 → 生成只读分享链接 / 导出
```

### 流程 B：旅行当天使用（行中）

```
打开首页 → 行程总览 → 点「第 2 天」卡片
   ↓
带着当天筛选状态进入地图工作台
   ↓
看到当天路线（彩色虚线 + 编号标记）
   ↓ 点「下一个地点」
   ↓
镜头飞近 + 详情卡展开（含导航跳转按钮）
   ↓
一键跳转外部地图导航
```

> **v1.1 移除**：原流程 C「回来后整理成纪念品」已删除。产品在 S2 结束后即完成交付，不承担行后环节。

## 八、页面级设计说明

### 8.1 首页 · 行程总览

**设计意图**：第一眼回答「这份行程是什么」——几天、去哪、每天怎么串。不做仪式感动画，做**信息密度合适的概览**。

- 顶部信息块：行程标题 + 一句说明 + **规模统计**（天数 / 地点数 / 周边餐饮数 / 建议停留合计）
- 每日路线卡（3 列，窄屏 1 列）：`第 N 天` + `主题` + `地点 A → B → C` + `建议停留合计约 X 小时`
- 每张日卡是**进入地图的入口**，点击后跳到地图工作台并自动切到当天
- 入场动效：信息块与卡片依次淡入上浮（约 550ms，逐级延迟 50–70ms），**可重播**

### 8.2 地图工作台

**布局**（桌面）

```
┌──────────────────────────────────────────────────────┐
│ [中国澳门 · 3 PLACES]                                 │
├────────────┬──────────────────────────┬──────────────┤
│            │                          │              │
│  行程面板   │       鸟瞰地图画布        │  地点详情卡   │
│  (320px)   │                          │   (360px)    │
│            │                          │              │
│ · 日期 Tab  │  · 倾斜 45–60° 视角       │  按需展开     │
│ · 路线摘要  │  · 3D 建筑               │              │
│ · 类型筛选  │  · 编号标记 1-1, 1-2…     │              │
│ · 地点列表  │  · 每日彩色虚线            │              │
│            │                          │              │
└────────────┴──────────────────────────┴──────────────┘
```

**布局**（移动端 < 768px）

- 地图全屏
- 行程面板从底部抽屉拉出（半屏 / 全屏两档）
- 详情卡从底部弹出，覆盖地图下半部
- 编号标记缩小，虚线加粗保证可见

**地图关键参数**

| 参数 | 取值 | 说明 |
|---|---|---|
| 初始 pitch | 50° | 倾斜鸟瞰，能看到建筑立体感 |
| 初始 zoom | 13 | 能看清街区与主要地标 |
| max pitch | 60° | 再高会看不清地名 |
| 建筑挤出 | 开启（3D buildings） | MapLibre + OpenFreeMap 即可实现（fill-extrusion 依赖瓦片里的建筑高度字段）；Mapbox 的立体质量与地形更好，但需 token 且收费 |
| 标记样式 | 圆形徽章，白底 + 当天主题色描边 | 内显编号如 `1-3` |
| 路线样式 | 虚线，宽度 3px，圆头 | 每天一色 |
| 镜头飞近 | `flyTo` + 缓动，时长 1200ms | 同时抬高 pitch 至 55°，强化「飞近」感 |

### 8.3 地点详情卡

固定结构（字段顺序不可变，保证浏览一致性）：

```
┌─────────────────────────────┐
│ [彩色头部块]                  │
│  英文小标：SHANGHAI FIELD GUIDE │
│  类型 · 气质：地标 · 石库门夜色   │
│  地点名：新天地（大字）          │
│  [时段 pill] [停留时长 pill]     │
├─────────────────────────────┤
│ 正文描述（2–3 句）              │
│ [配图]                        │
├─────────────────────────────┤
│ ☕ 先去吃什么                   │
│    店名 + 地址 + 一句提示        │
│ 🏞 去哪里看风景                 │
│    点位 + 一句提示              │
│ 查看资料来源 ↗                  │
└─────────────────────────────┘
```

**设计要点**：
- **头部块颜色随地点变化**（原文中愚园路是橙红、静安寺是姜黄、新天地是品红）——形成视觉记忆点
- 时段与停留时长用 pill 呈现，一眼可读
- 「查看资料来源 ↗」必须有，这是内容可信度的保障

### 8.4 路线自动排序（v1.1 新增 P0）

- 入口：行程面板底部的「自动排序」按钮，按天生效
- 算法：**最近邻构建初始路径 → 2-opt 消除交叉**，距离用 haversine
- 约束：支持**锁定锚点**（如酒店、预约制景点），锁定点不参与重排但在计算距离时作为必经点
- 输出：排序后即时更新路线虚线、地点列表顺序、标记编号
- 安全阀：排序前快照当前顺序，提供「撤销排序」回到手工顺序
- **必须显示排序收益**：如「总步行距离 8.4 km → 6.1 km，减少 27%」。没有可感知的收益，用户不会信任自动排序

### 8.5 交互边界（v1.1 明确不做）

以下能力**不在 v1 范围内**，写在这里是为了防止实现时「顺手加上」：

- 行后内容：手帐、照片墙、票根、纪念品、心情标签
- 多人协作编辑与评论
- 行程模板市场 / 社区分享
- 实时交通与拥堵规避

## 九、视觉设计规范

### 9.1 整体气质

**复古鲜活 + 手作感 + 轻微动态。**

关键词：老澳门街市感、葡式瓷砖、皮革质感、纸张纹理、荧光点缀、插画驱动。

> ⚠️ v1.1 待调：v1.0 的视觉关键词源自原文的上海调性（「老上海月份牌」）。
> 换成澳门后，插画与纹理方向应重新定位——候选是**葡式碎石路（calçada portuguesa）的波浪纹**
> 与**骑楼 / 瓷砖立面的青白配色**。这一条尚未定稿，见 §十三 待决策 4。

### 9.2 色彩

| 角色 | 色值 | 用途 |
|---|---|---|
| 纸张底 | `#F7F3E8` | 页面底色，带极轻纸张纹理 |
| 卡片白 | `#FFFFFF` | 卡片、面板 |
| 主点缀（荧光黄绿） | `#D8F13C` | 标题高亮块、按钮、强调 |
| 深墨 | `#1A1A1A` | 正文、标题 |
| 次墨 | `#6B6B6B` | 辅助文字 |
| 砖红 | `#C0392B` | Day 1 路线 / 暖色详情卡 |
| 赭橙 | `#E07B39` | Day 2 路线 / 暖色详情卡 |
| 靛蓝 | `#2C4A8F` | Day 3 路线 / 冷色详情卡 |
| 皮革棕 | `#6B4423` | 首页信息块底色（保留自 v1.0 的视觉资产） |

**规则**：
- 每天一个主题色，贯穿：路线虚线 → 编号标记描边 → 日期 Tab → 详情卡头部
- 荧光黄绿只用于**强调**，面积不超过页面的 10%
- 详情卡头部色从「每日主题色」派生，保证与当天路线同色系

### 9.3 字体

| 用途 | 字体 | 说明 |
|---|---|---|
| 中文标题 | 思源黑体 Heavy / 苹方 Semibold | 粗壮、有分量 |
| 中文正文 | 思源黑体 Regular | 行高 1.7 |
| 英文装饰小标 | 衬线体（如 Playfair Display）+ 大字距 | 如 `YOUR SHANGHAI JOURNEY` |
| 数字/编号 | 等宽或几何无衬线 | 编号徽章用 |

### 9.4 图形与插画

- **背景插画**：原创城市风格插画，必须原创（避免版权风险），带轻微动态（视差、云层漂移、灯光呼吸）
- **地点配图**：优先使用插画/建筑线稿，风格统一；照片需注明来源
- **装饰元素**：v1.1 后仅保留**纸张纹理**与**缝线**这类轻量元素。原「邮票 / 行李牌 / 拍立得边框」随行后记录一并移除

### 9.5 动效规范

| 动效 | 时长 | 缓动 | 备注 |
|---|---|---|---|
| 首页入场 | 550ms | cubic-bezier(0.22, 0.9, 0.24, 1) | 信息块与卡片逐级淡入上浮，可重播 |
| 镜头飞近 | 1200ms | cubic-bezier(0.4, 0, 0.2, 1) | 同时抬 pitch |
| 详情卡展开 | 300ms | ease-out | 从右侧滑入 |
| 路线虚线流动 | 循环 | linear | 强调「路径」感，可关闭 |
| 日期切换 | 400ms | ease-in-out | 地图标记渐隐渐现 |

⚠️ **必须提供「减少动效」开关**，尊重系统 `prefers-reduced-motion`。鸟瞰 + 飞近的组合对晕动症用户不友好。

### 9.6 无障碍底线

- 正文对比度 ≥ 4.5:1（纸张底 + 深墨已满足）
- 荧光黄绿**不可用于正文文字**（对比度不足），只能作背景块
- 所有交互元素有可见焦点态
- 地图信息必须有**列表替代视图**（不能只靠地图传达信息）

## 十、内容与资料来源规范

这是本产品区别于普通行程工具的核心资产，需单独规范。

### 地点内容模板（必填字段）

| 字段 | 必填 | 示例 |
|---|---|---|
| 名称 | ✅ | 新天地 |
| 类型 | ✅ | 地标 / 街巷 / 江岸 / 美食 / 博物馆 |
| 气质标签 | ✅ | 石库门夜色 |
| 建议时段 | ✅ | 傍晚至夜间 |
| 建议停留时长 | ✅ | 约 1.5 小时 |
| 正文描述 | ✅ | 2–3 句，讲清「为什么值得来」 |
| 先去吃什么 | ✅ | POLUX（太仓路 181 弄 5 号） |
| 去哪里看风景 | ✅ | — |
| 配图 | ✅ | 建筑插画或照片 |
| **资料来源** | ✅ | 链接 + 访问日期 |
| 避坑提示 | ⬜ | 如「周一闭馆」「需提前预约」 |

### 内容红线

1. **资料来源必须可追溯。** 每条地点信息都要有来源链接与访问日期，不允许「凭印象写」。
2. **价格、营业时间必须标注有效期。** 这类信息易变，须显示「最后核实于 YYYY-MM-DD」。
3. **不做虚假种草。** 不写「必去」「绝美」这类无信息量的词，写清楚**它是什么、适合什么时段、停留多久**。
4. **插画必须原创或已授权。** 不得直接使用他人摄影作品。

## 十一、迭代路线图

| 阶段 | 目标 | 交付物 | 成功标志 |
|---|---|---|---|
| **Phase 0** 验证 | 确认需求真实 | 可点击原型（Figma 或 HTML） | 5 位目标用户中 ≥3 位表示「会用」 |
| **Phase 1** MVP | 跑通「行前规划」主流程 | 单城市（澳门）+ 地点 + 行程 + 地图工作台 + 详情卡 | 用户能独立完成一次行程规划 |

**v1.1 路线图调整**：原 Phase 2「补全双主场（旅行箱 + 手帐）」整段删除，原 Phase 3 提效上移为 Phase 2，原 Phase 4 平台化上移为 Phase 3。产品不再需要「行后留存」这一环，路线图从 5 阶段收缩为 4 阶段。

**2026-09-27 进度**：Phase 1 与 Phase 2 的「路线自动排序」已跑通（原型见 `app/`）。
数据从上海示范集换为澳门实地行程（3 个地点，来源为用户提供的小红书笔记）。

**关键判断点**：Phase 1 结束后回访用户，验证的不再是「有没有人用行后手帐」，而是**「自动排序给出的路线，用户会不会照单全收」**。如果用户每次都要手工调整，说明排序算法的目标函数与真实偏好不一致——这是现在最大的产品风险。

### 功能验收

- [ ] 移动端 4G 弱网下首屏可加载（骨架屏 + 渐进增强）
- [ ] 离线状态下能打开已缓存的行程

### 质量验收

- [ ] Lighthouse 性能 ≥ 85（移动端）
- [ ] 所有地点信息有来源与核实日期
- [ ] 无版权风险的素材（插画原创 / 照片授权）
- [ ] 键盘可完成核心操作

原作者的实现方式是「用 AI 工具直接生成网站」，路径为：

1. 在千问中选择「工作」模式，调用「网页应用创建」Skill
