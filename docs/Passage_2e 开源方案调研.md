## 一、结论先行

**分两层回答，两层结论不一样，这点必须说清楚：**

| 层面 | 结论 | 说明 |
|---|---|---|
| **功能基座层面** | ✅ **存在**，且成熟度很高 | `liketrek/TREK` 对「行程编排 / 预订归集 / 预算记账 / 清单 / 票据文档 / 同行协作 / 地图路线 / 导出分享」8 项能力**全覆盖**，AGPL-3.0，一条 `docker run` 起服务，2026-09-26 仍在更新 |
| **产品形态层面** | ❌ **不存在** | 开源社区**没有**与小红书那篇对等的「视觉叙事型个人旅行工作台」——即「旅行箱」隐喻 + 原创城市插画 + 倾斜鸟瞰地图 + 电影式镜头推进 + 行后电子手帐这一整套体验。<br>⚠️ v1.1：其中「旅行箱」与「电子手帐」已被产品主动砍掉，见 `Passage_3b 决策·风险与缺口.md` §一（原 02 §十三） |

**因此本项目仍需要自建设计方案**，但要区分对待：

- **可直接复用的**：TREK 作为**功能基座与后端**（自托管部署），承担数据管理、协作、预算、附件、导出等重活。
- **必须自建的**：面向用户的**视觉与交互层**——也就是小红书那篇真正的价值所在。它是产品灵魂，开源社区没有替代品。

**如果只想快速拿到一个能用的旅行工作台**：直接部署 TREK 即可，今天就能用。
**如果要做成小红书那篇的样子**：TREK 当底座，前端重写。详见 `Passage_2 产品设计与信息架构.md`。

**唯一需要决策的约束**：TREK 是 **AGPL-3.0**。个人自托管、公司内部使用无限制；若基于它二开并以**网络服务形式对外提供**，修改部分须同协议开源。不接受则走「第四节」的 MIT 退路。

## 三、逐个要点

### TREK（首推功能基座）

- **行程编排**：地点可跨日期拖拽、日内排序并支持撤销；笔记与预订同样可拖；地图标记可直接拖到某一天。
- **地图与路线**：Leaflet / Mapbox GL / MapLibre GL 三选一（MapLibre + OpenFreeMap 无需 token）；3D 建筑与地形仅 Mapbox 支持；OSRM 路线自动排序（最近邻 + 2-opt，锁定锚点不动）；Transitous 公共交通；Open-Meteo 16 天天气。
- **预订与财务**：16 种预订类型；多段航班/火车含中转与时区（内置 4,045 个机场）；KItinerary 解析 EML/PDF/PKPass 确认单；费用按整数分拆分、多付款人、结算建议；汇率录入时冻结。
- **协作**：WebSocket 实时同步、权限矩阵（16 种操作 × 4 类角色）、邀请链接、公开只读分享、群聊/投票。
- **移动与离线**：PWA 可安装（无需应用商店）、离线读取（IndexedDB）、离线写入（`X-Idempotency-Key` 幂等重放）、离线地图瓦片预下载。
- **其他**：23 种语言（**含 zh 简体 / zh-TW 繁体**）、SSO/Passkey/TOTP、MCP 服务器（199 工具）、插件系统、GPX/ICS/PDF 导出。
- ⚠️ **注意**：README 明确多数功能是**管理员开关控制的 addon**。默认开启：Lists、Costs、Documents、Collab、Vacay、Atlas；**默认关闭**：Journey（游记）、Collections、MCP、AI Parsing、AirTrail。落地前需确认目标 addon 均已开启。

### AdventureLog

- 定位偏「**旅行足迹记录**」而非规划：地图打卡、国家/地区统计、步道 GPX、公开分享，含多日行程与航班/住宿/清单/日历视图。
- **没有预算记账、没有票据文档收纳、没有 PDF 导出**；无原生 App（Web 为主）。
- 中文翻译由 Weblate 社区维护，简中覆盖率约 99.9%。
- 适合「只想要足迹地图」的轻场景，或作为 Atlas 模块的设计参考。

### Wanderer

- README 明确定位为 **self-hosted trail database**，核心是上传/管理 GPS 轨迹与检索，规划只是附带功能。
- **不能当行程工作台用**。可作为「路线/轨迹」组件被其他系统引用。

### TRIP（itskovacs）

- **MIT 许可最宽松**，Docker 一条命令，含 OIDC。
- 功能极简：POI 地图 + 多日行程 + 协作；无预算 / 清单 / 文档 / 导出。
- 价值在于：**规避 AGPL 时的首选基座**。

### Firefly III

- 24.7k Star 的成熟个人复式记账系统。
- 可作旅行预算的**后端组件**，但需自行建立「行程 ↔ 账目」关联——它本身完全没有旅行概念。

### travel-plan-viz（中文，值得单列）

- 把行程生成**单文件、离线可用的 HTML**（地图 + 时间轴）。
- 与本项目「行程导出/分享」环节高度契合，思路值得直接借鉴——尤其「单文件 HTML」这个交付形态很讨巧。

## 四、缺口分析（以 TREK 为基准）

| 需求能力 | TREK | 说明 |
|---|---|---|
| 行程编排（多日 / 时间轴） | ✅ 已有 | 拖拽排期 + 日内重排序 + Markdown 日程笔记 |
| 机酒 / 门票预订归集 | ✅ 基本已有 | 16 类预订 + KItinerary 解析 + AirTrail 同步；门票/演出票是否单列类型未逐一确认 |
| 预算与记账 | ✅ 已有 | 分摊 + 结算建议 + 多币种 + CSV 导出 |
| 清单（行李 / 待办） | ✅ 已有 | 打包清单模板 + 待办优先级 / 提醒 |
| 票据与文档收纳 | ✅ 已有 | 附件挂载 + 回收站 + S3 可插拔存储 |
| 同行人协作 | ✅ 已有 | 实时同步 + 权限矩阵 + 邀请链接 + 公开只读分享 |
| 地图与路线 | ✅ 已有 | 多底图 + POI 检索 + OSRM 路线优化 + 公共交通 |
| 行程导出分享 | ✅ 已有 | GPX / ICS 订阅 / PDF / 公开链接 |
| **视觉叙事型体验**（旅行箱隐喻 / 原创插画 / 鸟瞰镜头） | ❌ **缺失** | 开源项目全部为「工具型」界面，无一带情感化视觉设计。⚠️ v1.1：其中「旅行箱」隐喻已砍，只保留鸟瞰镜头 |
| **地点内容运营**（吃/看/停留时长/资料来源） | ❌ **缺失** | TREK 只管理用户自己录入的地点，不含「攻略级」内容组织与来源标注。**v1.1 确认这是本项目最核心的护城河** |
| ~~**行后手帐 / 纪念品收纳**~~ | ✅ **不再是缺口** | ⚠️ v1.1：产品主动砍掉行后记录，此项已无需求。TREK 的 Journey addon 是否够用已不再是决策点 |
| 实时比价 / 真实票价抓取 | ❌ 缺失 | 需外挂航班 / OTA 抓取 |

**结论**：功能清单 8 项已 8/8 覆盖；v1.1 收敛后，缺口集中在**视觉体验**与**内容运营**两处。
后者（把攻略变成带来源的结构化地点）是这个产品真正难的部分，也是开源社区完全没有对应物的部分。

## 五、关键判断：为什么开源方案不能直接「照搬」

这是本次调研最重要的发现，需要单独说明。

**TREK 与小红书那篇，是两种不同的产品，不是同一个产品的不同实现。**

| 维度 | TREK（开源代表） | 小红书那篇 |
|---|---|---|
| 产品哲学 | **工具型**：帮你把旅行**管起来** | **叙事型**：帮你把旅行**记住并讲出来** |
| 界面气质 | 数据密集、功能导向、效率优先 | 情感化、插画驱动、探索优先 |
| 核心对象 | 行程 / 预订 / 费用 / 任务 | 地点 / 记忆 / 物件 / 心情 |
| 首屏 | 行程列表或仪表盘 | 一只打开的旅行箱 |
| 地图 | 平面地图 + 精确交互 | **倾斜鸟瞰 + 3D 建筑 + 镜头飞近** |
| 内容来源 | 用户自己录入 | **平台预置攻略**（吃/看/停留时长/来源） |
| 结束状态 | 旅行结束，数据归档 | 旅行结束，**变成一份纪念品** |
| 典型用户 | 多人出行、需要协作与算账的人 | 一个人或一对人、重视体验与记录的人 |

**所以：把 TREK 换一套皮肤，做不出小红书那篇。** 二者的信息架构从根上就不同——TREK 的主干是「行程 → 条目」，小红书那篇的主干是「旅行箱 → 物件 → 记忆」。

**正确的复用方式**：把 TREK 当**后端能力层**（数据、协作、预算、附件、导出、离线），在其上重建**面向体验的前端**。这样既省掉 80% 的工程工作量，又保住了产品的灵魂。

## 六、推荐复用策略

### 路径 A（推荐）：TREK 做基座 + 自建体验层

1. 自托管部署 TREK，开启需要的 addon（Lists / Costs / Documents / Collab / Atlas / Journey）。
2. 通过 TREK 的 **REST API 与 MCP 服务器**对接，自建前端消费其数据。
3. 自建部分：行程总览页、鸟瞰地图工作台、地点详情卡。~~电子手帐~~（v1.1 已砍）
4. 先跑官方 Demo（`demo.liketrek.com`）做功能验收，确认 API 覆盖度再决定二开深度。
5. ⚠️ 评估 AGPL-3.0：若对外提供网络服务，修改部分须同协议开源。

### 路径 B（规避 AGPL）：MIT 组合

- **itskovacs/TRIP**（MIT）作行程/地图基座 + **Spliit**（MIT）做分账 + 自建文档附件与导出。
- 预算模型可直接借鉴 Firefly III。
- 代价：需自行补齐清单、文档、导出三块，工程量显著高于路径 A。

### 路径 C（低成本验证）：模板方案

- 飞书多维表格「旅行计划」模板：免费、中文、协作原生，但**无地图、无离线、无自动路线**。
- 适合在正式开发前验证用户是否真的需要这个产品。

### 自建时应直接借鉴的设计

1. **数据模型**：抄 TREK 的「行程 → 日 → 地点/日程条目/预订/费用」五实体分层。
2. **预订解析**：抄 KItinerary 的思路（EML/PDF/PKPass → 结构化）。
3. **路线优化**：抄「最近邻 + 2-opt + 锁定锚点」。
4. **离线**：抄「IndexedDB 缓存 + `X-Idempotency-Key` 幂等重放」。
5. **单文件导出**：抄 travel-plan-viz 的「行程 → 离线 HTML」形态。

## 九、给下一步的建议

1. **先决策一件事**：要不要接受 AGPL-3.0。这决定走路径 A 还是 B。
2. **如果要做小红书那篇的形态**：直接进入 `Passage_2 产品设计与信息架构.md`，其中已把「复用 TREK 哪些能力、自建哪些部分」逐项对应。
3. **如果只想尽快能用**：直接部署 TREK，本系列文档转为「未来演进方向」参考。
